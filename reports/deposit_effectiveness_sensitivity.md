# Deposit-Effectiveness Sensitivity — the assumption bounds of the 2.0x claim

> Generated by `src/eval/deposit_effectiveness_sensitivity.py` on the frozen model and held-out test split. The frozen reports/README numbers are NOT changed — this is a pre-registered-style disclosure of what the headline ratio depends on.

## Why this exists

The entire financial result is a linear function of the DEPOSIT constants in `configs/cost_config.yaml` — `rto_reduction_pct = 0.80` (how well a deposit demand prevents an RTO) and `success_drop_pct = 0.40` (how many good customers abandon). These are **unvalidated industry priors**, not measurements. The repo's own `deposit_sensitivity.py` swept only the drop rate; the dominant constant (0.80) was never swept. This script sweeps both.

**Anchor check** at the claimed constants (r=0.8, d=0.4): primary EL savings ₹71,741 (frozen report: ₹71,741), best single-threshold = VERIFY_ADDRESS at ₹35,919 (frozen: ₹35,919) → ratio **2.00x** (frozen claim: 2.0x). The methodology reproduces the frozen numbers exactly.

- At the claimed drop rate (d=0.4), the ratio ranges **1.23x – 2.39x** across deposit effectiveness r ∈ [0.30, 0.90]: at r=0.30 the edge over a plain VERIFY threshold policy is only 1.23x, at r=0.50 it is 1.28x.
- Structural note: ratio ≥ 1 is guaranteed by construction — the argmin menu CONTAINS the binary VERIFY action space, so multi-action can never lose to any binary policy. The honest question is not *whether* it wins but *by how much*, and that is set by the assumed deposit effectiveness.
- **Menu degeneration**: below r ≈ **0.30** (d=0.4) the DEPOSIT band collapses below 1% of orders — the 'multi-action' router becomes a plain VERIFY threshold policy with extra steps. The 4-action story lives or dies with this one constant.
- Interpretation: the '2.0x' is an arithmetic consequence of assuming 80% deposit effectiveness. At r=0.5 the same pipeline yields ~1.3x; at r=0.3 it is ~1.2x. A production deployment must estimate r empirically (deposit-amount ladder A/B tests — see IMPROVEMENTS.md roadmap).

## 3. COD-fee revenue correction (omitted revenue, not a model change)

The frozen EL prices a delivered COD order at margin only and ignores the COD fee the customer pays (mean ₹48.97 on the test COD subset). If that fee is merchant revenue, every delivered COD order is more valuable than the model assumes, which shrinks the gains from intervening. Corrected at d=0.40:

## 4. What to do about this (ranked)

1. Stop presenting '2.0x' as a point estimate; present the range and the breakeven this script produces.
2. Estimate the constants empirically: deposit-amount ladder experiments (₹100/₹250/10% of value) with holdout geography; switchback designs for VERIFY.
3. Model heterogeneous effects (uplift / causal forests) once any logged intervention data exists — see `src/data/generator_v2.py` + `src/eval/stage6_uplift_ope.py` for the simulation-first demo of exactly that pipeline.
4. Expose COD-fee economics per merchant in the cost config rather than a global constant.
